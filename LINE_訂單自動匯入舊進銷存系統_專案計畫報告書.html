1. 專案摘要（Executive Summary）

1.1 核心目標

打通「線上叫瓦斯」到「店面舊進銷存系統」的最後一哩路，實現客戶在 LINE 送出訂單後，3～10 秒內全自動於店面舊進銷存系統建立正式叫貨單/出貨單並完成庫存扣減，徹底取代現行「人工看 Telegram 訊息、手動在電腦打單」的作業模式。

1.2 預期效益

  • 人工鍵單時間降為 0：節省每日早/晚叫氣尖峰 1.5 ~ 2.5 小時的人工作業時間。
  • 抄單錯誤率降為 0：杜絕人工打錯電話、地址、單價、折抵金額與鋼瓶規格的客訴。
  • 即時庫存與帳目同步：出貨紀錄秒級入帳，鋼瓶動態與每日營收帳目零延遲。

3. 系統整體架構與運作流程

🔒 金融級資安設計：主動輪詢拉取模式（Pull-Agent）
店面主機由內向外單向連線雲端領取訂單，店面電腦不向公網開放任何通訊埠（Port），杜絕任何被駭客或蠕蟲掃描攻擊的風險！
【客戶端 LINE】 │ (1) 客戶選規格數量送出訂單 ▼ 【雲端中樞 (Vercel + Google Sheets)】 │ (2) 訂單暫存待匯佇列 (狀態: 待確認 / imported: 否) │ │ (3) 店面主機每 5 秒主動安全向雲端拉單 (免固定 IP、免開 Port) ▼ 【店面主機本地 Ingest Daemon (Python)】 │ (4) 比對客戶編號 (舊客戶直接取 ID，新客戶自動建檔) │ (5) 本地 Transaction 寫入 SQL Server 訂單主檔與明細檔 ▼ 【店面舊系統 (127.0.0.1:1000)】✅ 自動入單、庫存扣減、列印出車單 │ │ (6) 回寫雲端狀態:「已匯入舊系統 (舊系統單號: ORD-XXXX)」 ▼ 【Telegram 派工群】&【客戶 LINE】收到入單確認推播

4. 核心模組技術規格

4.1 模組 A：店面本地「自動入單守護程式」（Ingest Daemon）

  • 程式檔案：shenglong_order_ingest_daemon.py
  • 取單循環：每 5 秒透過 HTTPS 安全呼叫雲端端點取得未入庫之訂單清單。
  • 防重檢驗（Idempotency）：以 orderId 作為防重唯一鍵，若資料庫已存在則略過，絕不重複扣庫存。
  • 新客自動補建：若電話未命中 dbo.customers，先自動配發客號並寫入客戶檔，再建立訂單。
  • 資料庫交易（Transaction）：主檔與明細檔包裹於同一 Transaction 內，確保資料一致性，寫入失敗自動 Rollback。

4.2 模組 B：雲端中樞佇列端點（Cloud Ingest API）

  • GET /api?action=pending-ingest-orders：供店面 Daemon 查詢未入庫訂單清單。
  • POST /api?action=mark-ingest-success：供店面 Daemon 回填舊系統單號與入庫時間。

4.3 模組 C：舊系統資料庫欄位對齊

  • 確認訂單主檔與明細檔表名（例：dbo.orders、dbo.order_details）。
  • 建立商品代碼對照表（50kg ➜ 舊品號、20kg ➜ 舊品號、16kg ➜ 舊品號、4kg ➜ 舊品號）。
  • 優惠折抵轉換為折讓項目或折讓欄位。

5. 例外情況與安全防呆機制

異常情境 潛在風險 系統防呆與容錯處置
店面主機斷網 / 關機 客人下單但電腦無法即時收到 雲端佇列持久化保存。主機開機恢復連網後，Daemon 自動依序批次補建，一筆不漏。
網路瞬斷重試 可能重複寫入兩張相同單據 以 orderId 進行唯一性比對，已存在直接略過，防重複扣庫存。
新客戶電話無客號 舊系統外鍵約束拒絕入單 Daemon 自動先行在 dbo.customers 建立新客資料並配發客號。
客戶線上取消訂單 客戶在 LINE 撤單，但舊系統已排單 即時推播 Telegram 派工警報；若舊系統已入單，自動標記為「作廢/取消」。

6. 三階段實施期程（Roadmap）

  1. 【第 1 階段：資料庫逆向與欄位對照】（1 個工作天）

    店面主機執行 SQL 結構分析腳本，確認訂單主檔名、明細檔名與瓦斯品號代碼。

  2. 【第 2 階段：程式開發與雲端端點擴充】（2 個工作天）

    開發雲端取單端點與店面 Python Ingest Daemon 常駐程式，串接 Telegram 入單成功通知。

  3. 【第 3 階段：沙盒測試與雙軌驗收】（2 個工作天）

    以測試單驗證舊進銷存畫面能否看見單據，進行 48 小時雙軌運行核對，正式啟用全自動化入單。
